What is the benefit for a processor of using the MMIO scheme to control I/O devices?

Your Answer

核心答案

MMIO（memory-mapped I/O，記憶體映射輸入輸出）把裝置的控制暫存器或資料介面配置到一般位址空間。處理器沿用原本的 load/store 指令、位址計算和資料路徑，便能存取記憶體或 I/O 裝置，不必為每一種裝置另設一組專用 I/O 指令。軟體看到的都是位址，實際由位址解碼與裝置介面決定要交給哪個裝置處理。因此，ISA 和程式的存取方式較一致，也方便增添新裝置。

步驟在本作業中的實際動作對應程式
1執行 load/store，計算有效位址 rs1 + offsetsrc/core.c 的 Core_execute()
2以完整實體位址查找所屬映射區間src/mem_map.c 的 MemoryMap_generic_load/store()
3位址減去裝置映射起點，得到裝置內部位移base_addr - mmap_unit_ptr->addr_bound.first
4透過裝置的 load/store 回呼處理請求AbstractMem_load/store()；由 ROM、MainMem 等各自實作

例如 src/core.c 的 load/store 分支會先形成有效位址，再交給統一的記憶體映射介面（此段在原版及改良版均相同）：

MemoryMap_generic_load(&self->mem_map, a + imm_i, length, bytes);
/* STORE 分支： */
MemoryMap_generic_store(&self->mem_map, a + imm_s, length, bytes);

其中 a 是事先讀取的 gpr[rs1]；imm_i、imm_s 分別是 LOAD 的 I-type 偏移和 STORE 的 S-type 偏移；length 決定一次讀寫 1、2 或 4 個位元組。核心不需知道目標是 ROM 還是 RAM；同樣的入口也可以對應文字輸出與停止旗標等 MMIO 裝置。

src/mem_map.c 的位址派送關鍵片段如下：

if ((base_addr >= self->memory_map_arr[i].addr_bound.first) &&
    (base_addr + length <= self->memory_map_arr[i].addr_bound.second)) {
    mmap_unit_ptr = &self->memory_map_arr[i];
}
AbstractMem_load(mmap_unit_ptr->device_ptr,
                 base_addr - mmap_unit_ptr->addr_bound.first, length, buffer);

這段程式先確定完整存取範圍都落在同一個裝置的區間，然後以裝置相對位址呼叫 load。store 採相同路徑、改呼叫 AbstractMem_store()。限制是 MMIO 位址仍須由軟體依裝置規格使用；某些裝置讀寫可能具有副作用，並非每個映射位址都能當一般 RAM 任意存取。

Your Answer

核心答案

「架構可見狀態」是執行程式可以透過 ISA 觀察或影響、且執行下一條指令所需依賴的狀態。在此 Lab 1 的 RV32I 模擬器中，主要包括 32 個通用暫存器、PC，以及透過 load/store 可觀察的記憶體與映射裝置狀態。每執行一步，指令依舊狀態產生新狀態；若任一項更新錯誤，後續指令的運算、資料或控制流程都可能偏離原程式。

PCself->arch_state.current_pc指定下一條要讀取的指令；分支與跳躍會改變控制流程

從 Core_fetch() 可看出 PC 的直接作用：

                       self->arch_state.current_pc, 4, inst_in_bytes);

這一行從 PC 指向的位址讀取 4 個位元組機器碼。Core_execute() 一開始設定 new_pc = current_pc + 4；條件分支成立、JAL 或 JALR 會覆寫它。最後 Core_update_pc() 才將新 PC 提交：

static void Core_update_pc(Core *self) {
    self->arch_state.current_pc = self->new_pc;
}

對暫存器的寫回，程式有明確的 x0 保護：

Why does RISC-V define conditional-set instructions? Can branch instructions alone achieve the same functionality? If yes, what is the benefit of having the additional conditional-set instructions?

Your Answer

核心答案

條件設定（conditional-set）指令把比較結果直接寫進暫存器：條件成立寫 1，否則寫 0。本作業的 SLT、SLTU、SLTI、SLTIU 分別支援有號／無號、暫存器／立即數比較。條件分支也能透過兩條控制路徑算出相同的 0 或 1，但通常需要額外指令和標籤；條件設定則保持順序執行的 PC，結果可直接給後續指令使用。

指令比較運算元比較語意結果
slt rd, rs1, rs2兩個暫存器有號小於成立 rd=1，否則 0
sltu rd, rs1, rs2兩個暫存器無號小於同上
slti rd, rs1, imm暫存器與符號延伸的立即數有號小於同上
sltiu rd, rs1, imm暫存器與符號延伸的立即數無號小於同上

Core_execute() 對應的實作（節錄）：

case inst_slt:   result = (int32_t)a < (int32_t)b; break;
case inst_sltu:  result = a < b; break;
case inst_slti:  result = (int32_t)a < (int32_t)imm_i; break;
case inst_sltiu: result = a < imm_i; break;

a、b 是 32 位元暫存器原值；(int32_t) 讓有號比較把最高位解讀為符號位。SLTIU 仍先符號延伸 12 位元立即數，之後才把 32 位元位元模式拿去做無號比較。例如立即數 -1 經符號延伸後成為 0xffffffff；若 a=0，無號比較 0 < 0xffffffff 為真，因此結果是 1。

分支的等價寫法（示意：比較 x1<x2，結果放 x3）需安排不同控制流程：

addi x3, x0, 0
blt  x1, x2, true_case
jal  x0, done
true_case:
addi x3, x0, 1
done:

直接使用 slt x3, x1, x2 即可產生同一布林結果；實際執行成本仍取決於處理器實作與編譯器最佳化，不能宣稱所有硬體一定更快。若只是決定是否跳躍，直接使用 branch 可能最合適；若後續需要數值 0/1，conditional-set 較直接。

Consider jalr xN, xN, imm, where N is a positive number from 1 to 31. What potential problem might arise when implementing JALR in an ISS?

Your Answer

核心答案

jalr xN, xN, imm 的 rd 與 rs1 指向同一個暫存器。JALR 同時要產生兩個結果：跳躍目標使用執行前的 xN，而連結位址 old_pc + 4 要寫回 xN。若 ISS 先把 pc+4 寫到 xN，再讀 xN 計算目標，就會把剛寫入的連結位址誤當舊基底，跳到錯誤位置。

時序正確做法錯誤做法
讀 rs1先保存 old_xN尚未讀取
目標(old_xN + sign_extend(imm)) & ~1(old_pc+4 + sign_extend(imm)) & ~1
寫 rd最後寫入 old_pc + 4過早寫入，破壞目標運算元

本作業的 Core_execute() 先在 switch 前讀取來源值：

const unsigned rd = (raw >> 7) & 31u;
const unsigned rs1 = (raw >> 15) & 31u;
const reg_t a = self->arch_state.gpr[rs1];
self->new_pc = self->arch_state.current_pc + 4;

JALR 分支先計算下一個 PC，統一寫回在 switch 後執行：

case inst_jalr:
    result = self->new_pc;
    self->new_pc = (a + imm_i) & ~1u;
    break;
/* switch 結束後 */
if (write_rd && rd != 0) self->arch_state.gpr[rd] = result;

例如舊 PC 為 0x00000100、舊 x5=0x00000200、imm=3，執行 jalr x5, x5, 3 應得到新 PC (0x200+3)&~1 = 0x202、新 x5=0x104。若先寫 x5=0x104，錯誤目標就變成 (0x104+3)&~1 = 0x106。遮罩 & ~1u 會強制清除目標位址最低位；imm_i 必須先符號延伸。最後 Core_update_pc() 才將計算好的 new_pc 提交。

概念图解

最低位固定为 0，因此无需占用指令编码栏位；重组 immediate 时直接补 0。

Why do the encoding formats for JAL and BRANCH instructions omit imm[0]?

Your Answer

核心答案

JAL 的 J-type 偏移與 BRANCH 的 B-type 偏移，重組後最低位 imm[0] 都固定為 0；也就是目標相對偏移以 2 bytes 為最小編碼單位。既然最低位不是自由變動的資料，就沒有必要用一個機器碼欄位儲存它。把欄位留給較高位的偏移，可在固定 32 位元指令長度下涵蓋較大的相對跳躍距離。這種半字（16 位元）對齊也與可選的壓縮指令擴充相容；本實驗只執行 32 位元指令，不代表編碼中必須額外存一個恆為零的 bit。

編碼整數偏移的位元配置imm[0]計算下一個 PC
B-type（BEQ 等）`imm[1210:54:1110]`隱含 0old_pc + sign_extend(imm_b)，分支成立時
J-type（JAL）`imm[2019:121110:10]`隱含 0old_pc + sign_extend(imm_j)

src/core.c 以左移 1 重組最低幾位，沒有把任何位元放在位置 0（節錄自改良版 core_improved.c）：

const reg_t imm_b = sign_extend(((raw >> 31) << 12) |
                                 (((raw >> 7) & 1u) << 11) |
                                 (((raw >> 25) & 0x3fu) << 5) |
                                 (((raw >> 8) & 0xfu) << 1), 13);

const reg_t imm_j = sign_extend(((raw >> 31) << 20) |
                                 (((raw >> 12) & 0xffu) << 12) |
                                 (((raw >> 20) & 1u) << 11) |
                                 (((raw >> 21) & 0x3ffu) << 1), 21);

其中 sign_extend(value, width) 使用無號運算將位元圖樣擴展為 32 位元；B-type 使用 13 位、J-type 使用 21 位。B-type 的 raw[7] 放到 imm[11]；J-type 的 raw[20] 放到 imm[11]。由於最高位仍需符號延伸，正負位移都能以目前 PC 為基準跳向前或向後。JALR 不屬於這兩種立即數編碼：它採 I-type 偏移加 rs1，然後將目標位址的 bit 0 清為零，不可把兩種規則混為一談。

What is the benefit for a processor of using the MMIO scheme to control I/O devices?

Question 3

Why does RISC-V define conditional-set instructions? Can branch instructions alone achieve the same functionality? If yes, what is the benefit of having the additional conditional-set instructions?

Your Answer

核心答案

條件設定（conditional-set）指令把比較結果直接寫進暫存器：條件成立寫 1，否則寫 0。本作業的 SLT、SLTU、SLTI、SLTIU 分別支援有號／無號、暫存器／立即數比較。條件分支也能透過兩條控制路徑算出相同的 0 或 1，但通常需要額外指令和標籤；條件設定則保持順序執行的 PC，結果可直接給後續指令使用。

指令比較運算元比較語意結果
slt rd, rs1, rs2兩個暫存器有號小於成立 rd=1，否則 0
sltu rd, rs1, rs2兩個暫存器無號小於同上
slti rd, rs1, imm暫存器與符號延伸的立即數有號小於同上
sltiu rd, rs1, imm暫存器與符號延伸的立即數無號小於同上

Core_execute() 對應的實作（節錄）：

case inst_slt:   result = (int32_t)a < (int32_t)b; break;
case inst_sltu:  result = a < b; break;
case inst_slti:  result = (int32_t)a < (int32_t)imm_i; break;
case inst_sltiu: result = a < imm_i; break;

a、b 是 32 位元暫存器原值；(int32_t) 讓有號比較把最高位解讀為符號位。SLTIU 仍先符號延伸 12 位元立即數，之後才把 32 位元位元模式拿去做無號比較。例如立即數 -1 經符號延伸後成為 0xffffffff；若 a=0，無號比較 0 < 0xffffffff 為真，因此結果是 1。

分支的等價寫法（示意：比較 x1<x2，結果放 x3）需安排不同控制流程：

addi x3, x0, 0
blt  x1, x2, true_case
jal  x0, done
true_case:
addi x3, x0, 1
done:

直接使用 slt x3, x1, x2 即可產生同一布林結果；實際執行成本仍取決於處理器實作與編譯器最佳化，不能宣稱所有硬體一定更快。若只是決定是否跳躍，直接使用 branch 可能最合適；若後續需要數值 0/1，conditional-set 較直接。

Question 5

Consider jalr xN, xN, imm, where N is a positive number from 1 to 31. What potential problem might arise when implementing JALR in an ISS?

Your Answer

核心答案

jalr xN, xN, imm 的 rd 與 rs1 指向同一個暫存器。JALR 同時要產生兩個結果：跳躍目標使用執行前的 xN，而連結位址 old_pc + 4 要寫回 xN。若 ISS 先把 pc+4 寫到 xN，再讀 xN 計算目標，就會把剛寫入的連結位址誤當舊基底，跳到錯誤位置。

時序正確做法錯誤做法
讀 rs1先保存 old_xN尚未讀取
目標(old_xN + sign_extend(imm)) & ~1(old_pc+4 + sign_extend(imm)) & ~1
寫 rd最後寫入 old_pc + 4過早寫入，破壞目標運算元

本作業的 Core_execute() 先在 switch 前讀取來源值：

const unsigned rd = (raw >> 7) & 31u;
const unsigned rs1 = (raw >> 15) & 31u;
const reg_t a = self->arch_state.gpr[rs1];
self->new_pc = self->arch_state.current_pc + 4;

JALR 分支先計算下一個 PC，統一寫回在 switch 後執行：

case inst_jalr:
    result = self->new_pc;
    self->new_pc = (a + imm_i) & ~1u;
    break;
/* switch 結束後 */
if (write_rd && rd != 0) self->arch_state.gpr[rd] = result;

例如舊 PC 為 0x00000100、舊 x5=0x00000200、imm=3，執行 jalr x5, x5, 3 應得到新 PC (0x200+3)&~1 = 0x202、新 x5=0x104。若先寫 x5=0x104，錯誤目標就變成 (0x104+3)&~1 = 0x106。遮罩 & ~1u 會強制清除目標位址最低位；imm_i 必須先符號延伸。最後 Core_update_pc() 才將計算好的 new_pc 提交。

Question 6 (2 pts for bonus)

Why do the encoding formats for JAL and BRANCH instructions omit imm[0]?

Your Answer

核心答案

JAL 的 J-type 偏移與 BRANCH 的 B-type 偏移，重組後最低位 imm[0] 都固定為 0；也就是目標相對偏移以 2 bytes 為最小編碼單位。既然最低位不是自由變動的資料，就沒有必要用一個機器碼欄位儲存它。把欄位留給較高位的偏移，可在固定 32 位元指令長度下涵蓋較大的相對跳躍距離。這種半字（16 位元）對齊也與可選的壓縮指令擴充相容；本實驗只執行 32 位元指令，不代表編碼中必須額外存一個恆為零的 bit。

編碼整數偏移的位元配置imm[0]計算下一個 PC
B-type（BEQ 等）`imm[1210:54:1110]`隱含 0old_pc + sign_extend(imm_b)，分支成立時
J-type（JAL）`imm[2019:121110:10]`隱含 0old_pc + sign_extend(imm_j)

src/core.c 以左移 1 重組最低幾位，沒有把任何位元放在位置 0（節錄自改良版 core_improved.c）：

const reg_t imm_b = sign_extend(((raw >> 31) << 12) |
                                 (((raw >> 7) & 1u) << 11) |
                                 (((raw >> 25) & 0x3fu) << 5) |
                                 (((raw >> 8) & 0xfu) << 1), 13);

const reg_t imm_j = sign_extend(((raw >> 31) << 20) |
                                 (((raw >> 12) & 0xffu) << 12) |
                                 (((raw >> 20) & 1u) << 11) |
                                 (((raw >> 21) & 0x3ffu) << 1), 21);

其中 sign_extend(value, width) 使用無號運算將位元圖樣擴展為 32 位元；B-type 使用 13 位、J-type 使用 21 位。B-type 的 raw[7] 放到 imm[11]；J-type 的 raw[20] 放到 imm[11]。由於最高位仍需符號延伸，正負位移都能以目前 PC 為基準跳向前或向後。JALR 不屬於這兩種立即數編碼：它採 I-type 偏移加 rs1，然後將目標位址的 bit 0 清為零，不可把兩種規則混為一談。

### 核心答案

條件設定（conditional-set）指令把比較結果直接寫進暫存器：條件成立寫 `1`，否則寫 `0`。本作業的 `SLT`、`SLTU`、`SLTI`、`SLTIU` 分別支援有號／無號、暫存器／立即數比較。條件分支也能透過兩條控制路徑算出相同的 0 或 1，但通常需要額外指令和標籤；條件設定則保持順序執行的 PC，結果可直接給後續指令使用。

| 指令 | 比較運算元 | 比較語意 | 結果 |
|---|---|---|---|
| `slt rd, rs1, rs2` | 兩個暫存器 | 有號小於 | 成立 `rd=1`，否則 `0` |
| `sltu rd, rs1, rs2` | 兩個暫存器 | 無號小於 | 同上 |
| `slti rd, rs1, imm` | 暫存器與符號延伸的立即數 | 有號小於 | 同上 |
| `sltiu rd, rs1, imm` | 暫存器與符號延伸的立即數 | 無號小於 | 同上 |

`Core_execute()` 對應的實作（節錄）：

```c
case inst_slt:   result = (int32_t)a < (int32_t)b; break;
case inst_sltu:  result = a < b; break;
case inst_slti:  result = (int32_t)a < (int32_t)imm_i; break;
case inst_sltiu: result = a < imm_i; break;
```

`a`、`b` 是 32 位元暫存器原值；`(int32_t)` 讓有號比較把最高位解讀為符號位。`SLTIU` **仍先符號延伸 12 位元立即數**，之後才把 32 位元位元模式拿去做無號比較。例如立即數 `-1` 經符號延伸後成為 `0xffffffff`；若 `a=0`，無號比較 `0 < 0xffffffff` 為真，因此結果是 `1`。

分支的等價寫法（示意：比較 `x1<x2`，結果放 `x3`）需安排不同控制流程：

```asm
addi x3, x0, 0
blt  x1, x2, true_case
jal  x0, done
true_case:
addi x3, x0, 1
done:
```

直接使用 `slt x3, x1, x2` 即可產生同一布林結果；實際執行成本仍取決於處理器實作與編譯器最佳化，不能宣稱所有硬體一定更快。若只是決定是否跳躍，直接使用 branch 可能最合適；若後續需要數值 0/1，conditional-set 較直接。

### Question 4

**What is the difference between `ROM` and `MainMem`? Answer this question by tracing the source code.**

#### Your Answer

### 追蹤原始碼的答案

本專案的 `ROM` 和 `MainMem` 都繼承同一個抽象記憶體介面，均可被 MemoryMap 定位並讀取；關鍵差異在 **CPU 經由記憶體映射寫入時的行為**：ROM 的 store 回呼直接拒絕修改，MainMem 的 store 回呼則將位元組寫入陣列。此處描述的是這份模擬器的軟體實作，而不是所有實體 ROM/RAM 的電路細節。

| 項目 | ROM | MainMem |
|---|---|---|
| 定義檔 | `src/rom.h` | `src/main_mem.h` |
| 映射基底 | `0x00000000` | `0x80000000` |
| 容量 | `0x1000` = 4096 bytes | `0x10000` = 65536 bytes |
| CPU load | 從 `rom[]` 複製 bytes | 從 `mem[]` 複製 bytes |
| CPU store | `Panic("ROM should not be modified!")` | 將資料寫回 `mem[]` |
| 建構時 | 將內部陣列清為 0 | 將內部陣列清為 0 |

**第一步：註冊位址。**`src/iss.c` 的 `ISS_ctor()` 建立兩個裝置，並各自註冊半開區間 `[base, base + size)`：

```c
mmap_unit_t ROM_mmap_unit = { .addr_bound = { .first = ROM_MMAP_BASE,
                                              .second = ROM_MMAP_BASE + ROM_SIZE },
                              .device_ptr = (AbstractMem *)&self_->rom_mmio };
Core_add_device(&self_->core, ROM_mmap_unit);
```

MainMem 的註冊方式相同，改用 `MAIN_MEM_MMAP_BASE`、`MAIN_MEM_SIZE` 與 `main_mem_mmio`。大小和基底來自各自的 `.h` 檔；例如 `ROM_SIZE 0x1000`，因此合法區間最後一個位址是 `0x00000fff`。

**第二步：路由存取。**`src/mem_map.c` 的 `MemoryMap_generic_load/store()` 掃描範圍，找到所屬裝置，將完整位址減去映射基底後，透過 `AbstractMem_load/store()` 派送。例如 CPU 寫入 `0x80000004`，MainMem 收到內部偏移 `4`。

**第三步：裝置決定行為。**`src/rom.c` 的關鍵程式是：

```c
DECLARE_ABSTRACT_MEM_LOAD(ROM) {
    ROM *self_ = container_of(self, ROM, super);
    for (int i = 0; i < length; i++)
        buffer[i] = self_->rom[base_addr + i];
}
DECLARE_ABSTRACT_MEM_STORE(ROM) {
    Panic("ROM should not be modified!");
}
```

`src/main_mem.c` 的 store 則有實際寫回：

```c
DECLARE_ABSTRACT_MEM_STORE(MainMem) {
    MainMem *self_ = container_of(self, MainMem, super);
    for (int i = 0; i < length; i++)
        self_->mem[base_addr + i] = ref_data[i];
}
```

程式還在各回呼中檢查裝置內存取範圍。`ISS_ctor()` 呼叫 `load_elf(elf_file_name, self_->rom_mmio.rom, ROM_SIZE, &self_->core.arch_state.current_pc)`，是**啟動時直接取得 ROM 陣列供載入器填入映像**；它並不等於程式執行期間以 store 指令寫 ROM。因此「ROM 可在初始化時載入程式」與「CPU 不可對 ROM 做一般 store」沒有矛盾。

### Question 5

**Consider `jalr xN, xN, imm`, where N is a positive number from 1 to 31. What potential problem might arise when implementing JALR in an ISS?**

#### Your Answer

### 核心答案

`jalr xN, xN, imm` 的 `rd` 與 `rs1` 指向同一個暫存器。JALR 同時要產生兩個結果：跳躍目標使用執行前的 `xN`，而連結位址 `old_pc + 4` 要寫回 `xN`。若 ISS 先把 `pc+4` 寫到 `xN`，再讀 `xN` 計算目標，就會把剛寫入的連結位址誤當舊基底，跳到錯誤位置。

| 時序 | 正確做法 | 錯誤做法 |
|---|---|---|
| 讀 rs1 | 先保存 `old_xN` | 尚未讀取 |
| 目標 | `(old_xN + sign_extend(imm)) & ~1` | `(old_pc+4 + sign_extend(imm)) & ~1` |
| 寫 rd | 最後寫入 `old_pc + 4` | 過早寫入，破壞目標運算元 |

本作業的 `Core_execute()` 先在 switch 前讀取來源值：

```c
const unsigned rd = (raw >> 7) & 31u;
const unsigned rs1 = (raw >> 15) & 31u;
const reg_t a = self->arch_state.gpr[rs1];
self->new_pc = self->arch_state.current_pc + 4;
```

JALR 分支先計算下一個 PC，統一寫回在 switch 後執行：

```c
case inst_jalr:
    result = self->new_pc;
    self->new_pc = (a + imm_i) & ~1u;
    break;
/* switch 結束後 */
if (write_rd && rd != 0) self->arch_state.gpr[rd] = result;
```

例如舊 PC 為 `0x00000100`、舊 `x5=0x00000200`、`imm=3`，執行 `jalr x5, x5, 3` 應得到新 PC `(0x200+3)&~1 = 0x202`、新 `x5=0x104`。若先寫 `x5=0x104`，錯誤目標就變成 `(0x104+3)&~1 = 0x106`。遮罩 `& ~1u` 會強制清除目標位址最低位；`imm_i` 必須先符號延伸。最後 `Core_update_pc()` 才將計算好的 `new_pc` 提交。

### Question 6 (2 pts for bonus)

**Why do the encoding formats for JAL and BRANCH instructions omit `imm[0]`?**

#### Your Answer

### 核心答案

JAL 的 J-type 偏移與 BRANCH 的 B-type 偏移，重組後最低位 `imm[0]` 都固定為 0；也就是目標相對偏移以 **2 bytes** 為最小編碼單位。既然最低位不是自由變動的資料，就沒有必要用一個機器碼欄位儲存它。把欄位留給較高位的偏移，可在固定 32 位元指令長度下涵蓋較大的相對跳躍距離。這種半字（16 位元）對齊也與可選的壓縮指令擴充相容；本實驗只執行 32 位元指令，不代表編碼中必須額外存一個恆為零的 bit。

| 編碼 | 整數偏移的位元配置 | `imm[0]` | 計算下一個 PC |
|---|---|---|---|
| B-type（BEQ 等） | `imm[12|10:5|4:1|11|0]` | 隱含 0 | `old_pc + sign_extend(imm_b)`，分支成立時 |
| J-type（JAL） | `imm[20|19:12|11|10:1|0]` | 隱含 0 | `old_pc + sign_extend(imm_j)` |

`src/core.c` 以左移 1 重組最低幾位，沒有把任何位元放在位置 0（節錄自改良版 `core_improved.c`）：

```c
const reg_t imm_b = sign_extend(((raw >> 31) << 12) |
                                 (((raw >> 7) & 1u) << 11) |
                                 (((raw >> 25) & 0x3fu) << 5) |
                                 (((raw >> 8) & 0xfu) << 1), 13);

const reg_t imm_j = sign_extend(((raw >> 31) << 20) |
                                 (((raw >> 12) & 0xffu) << 12) |
                                 (((raw >> 20) & 1u) << 11) |
                                 (((raw >> 21) & 0x3ffu) << 1), 21);
```

其中 `sign_extend(value, width)` 使用無號運算將位元圖樣擴展為 32 位元；B-type 使用 13 位、J-type 使用 21 位。B-type 的 `raw[7]` 放到 `imm[11]`；J-type 的 `raw[20]` 放到 `imm[11]`。由於最高位仍需符號延伸，正負位移都能以目前 PC 為基準跳向前或向後。JALR 不屬於這兩種立即數編碼：它採 I-type 偏移加 `rs1`，然後將**目標位址**的 bit 0 清為零，不可把兩種規則混為一談。

### Your Reflection

這份作業使我把「ISA 對程式承諾的行為」和「模擬器內部實作步驟」連在一起理解。每次 tick 都依序 Fetch、Decode、Execute、更新 PC：Fetch 要正確依小端序組出 32 位元指令；Decode 要看 opcode、funct3 與 funct7；Execute 要區分算術、記憶體和控制流程的副作用。表面看起來一條指令只要做一次運算，實際上還要保證暫存器、PC、記憶體及 `x0` 在每步結束後符合規格。

我最需要反覆核對的是四個細節。第一，I/S/B/J 立即數散布在不同 bit 位置，必須依格式重組並處理符號延伸；尤其 B/J 的 bit 0 固定為零。第二，`LB`/`LH` 與 `LBU`/`LHU` 讀相同數量的位元組，但對最高資料位的延伸規則不同：例如位元組 `0x80` 以 LB 讀得 `0xffffff80`，以 LBU 讀得 `0x00000080`。第三，有號與無號比較及 `SRA`/`SRL` 右移必須分開實作。第四，`jalr rd, rs1, imm` 在 `rd==rs1` 時必須先保存舊運算元，再更新連結暫存器。將來源值先存於 `a`、`b`，並將寫回集中於 switch 後，讓這些資料相依關係較容易檢查。
